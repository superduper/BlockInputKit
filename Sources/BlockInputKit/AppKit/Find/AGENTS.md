## Find Scope

- `BlockInputFindController` owns query, ordered matches, and the active index (pure navigation with wrap-around); `BlockInputView+Find` drives selection/scroll, and the highlight files paint temporary `.backgroundColor` match chrome on visible/configured items only. `BlockInputSearch` matches the document as the reader sees it: a link/image `[title](url)` contributes only its visible title/alt text (the brackets, parens, and URL/destination are excluded via `BlockInputInlineMarkdownParsing.linkRanges`), so find/replace never touch a destination.
- Re-apply match highlight from `configureBlockItem` when find is active; keep the find background attribute store independent from `temporarySelectionHighlightRange`, and the active match must read stronger than inactive ones. When a block's text changes while find is active, call `refreshFindMatchesAfterDocumentEdit()` (recompute + re-highlight WITHOUT moving the caret) so an edited-away match drops its stale highlight. Reveal scrolls an off-screen match into view via `scrollFindMatchBlockIntoView` (collection `scrollToItems`, robust before lazy content height is realized).
- The find bar (`BlockInputFindBarView`) is a top-anchored child of `BlockInputView`, not part of the link/image modal machinery. `presentFindBar`/`dismissFindBar` own bar lifecycle and first-responder hand-off; `endFind` clears state. Cmd+F/G dispatch lives in `handleFindKeyEquivalent`, called from `performEditorKeyEquivalentDefaults` AFTER host `keyboardShortcuts` so a host Cmd+F still wins. Gate all of this behind `findEnabled`.
- The dim find scrim (`BlockInputFindScrimView`, installed by `BlockInputView+FindScrim`) is a full-bleed DIRECT child of `BlockInputView`, positioned BELOW the find bar — NOT a child of `editorChromeView` (which is `isHidden` when the host configures no chrome surface, which would hide the scrim). It MUST keep `hitTest -> nil`. Recompute its punch-through holes from visible match rects only on query/navigation/scroll/configure (`updateFindScrim`); text-block rects come from the layout manager, table matches fall back to the item's whole frame. A genuine user click into a block (`blockItemDidBeginEditing`) calls `dismissFindDimForUserInteraction()`, which removes the dim + active-match overlay but KEEPS highlights and find state.
- The active-match emphasis overlay (`BlockInputFindActiveMatchView`, installed by `BlockInputView+FindActiveMatch`) is a direct child of `BlockInputView`, *above* the scrim and below the bar, and also keeps `hitTest -> nil`. `updateFindActiveMatchOverlay(animated:)` measures only the single active match's rect (via `findMatchRect`) and pulses (subtle 1.15->1.0 scale about the rect center) ONLY on land; scroll-driven repositioning passes `animated: false` and must NOT pulse.
- Vim search (`BlockInputVimSearchLineView` + `BlockInputView+VimSearch`) is highlight-only and reuses the find engine (matches, highlights, `findNext`/`findPrevious`) but NO bar, scrim, or zoom overlay. The line is a display-only bottom-leading child of `BlockInputView` (`hitTest -> nil`) showing `/<query>` while typing and `<query>  current/total` after commit. `beginVimSearch` resets find then shows `/`; `updateVimSearch` calls `recomputeFindMatches(query:)` (controller update + `applyFindHighlights()` WITHOUT moving the caret or installing scrim/overlay) — the caret only moves on `commitVimSearch` (reveals the active match). `cancelVimSearch`/`clearVimSearchHighlight` clear via `endFind` and hide the line. `advanceActiveMatch` calls `refreshVimSearchLineCount()`, a no-op unless the vim line is present, so the Cmd+F bar path is undisturbed.
- Replace lives in `BlockInputView+FindReplace`: `replaceCurrentMatch(with:)` rewrites the active match's UTF-16 source range (raw `replacingCharacters`, table-safe — never touches pipes) via one `applyGranularBlockReplacement` + `registerBlockReplacementStructuralEdit`; `replaceAllMatches(with:)` groups matches by block, replaces each block's ranges in descending-location order to build one `afterBlock` per block, and applies them as a single multi-block edit so one undo reverts all. Both gate on `findEnabled`/`isEditable`, then recompute via `updateFindQuery` (preserving find-field focus). Replace is gated by a labeled `Replace` CHECKBOX in the find row (next to count/nav); checking it reveals the replace row (`replaceField` + Replace/Replace All) and grows the bar height. Escape from EITHER field closes the bar (and tears down find + the dim); Return in the replace field performs Replace. The bar owns its `desiredHeight`/`heightConstraint`; no new `BlockInputView` stored properties.
